# Security and privacy

This is a developer preview. The application, native bridge and packaged dependencies have not received an independent security audit. Use disposable wallets while evaluating the code. Public source makes independent review possible.

## Reporting a problem

Use [GitHub private vulnerability reporting](https://github.com/harvard1932/xmr-monero-wallet/security/advisories/new) for security issues. Include the commit, device and iOS version, and the behavior you observed. Keep seed words, wallet files, view keys, transaction QR frames and access tokens private.

## What stays on the phone

* Wallet2 creates keys, scans blocks and prepares and signs transactions locally. Each wallet has a random wallet2 password encrypted under a device-local wallet unlock key. The app PIN protects that key with PBKDF2-HMAC-SHA256 (600,000 rounds), a random salt and AES-GCM. Its envelope and retry counter live in the device-only, passcode-bound iOS Keychain. The app records attempts before verification, delays repeated attempts, and locks PIN entry after ten failures. PIN reset requires the device passcode. Optional Face ID or Touch ID requires a fresh biometric match and uses that same authenticated context to access a separate Keychain item bound to the current enrollment. The app also checks the saved enrollment state when iOS supplies it. When iOS reports a missing or changed enrollment, the app requires the PIN to enable biometrics again. The app requests fresh authentication to reveal backups, display private pairing information, sign or broadcast.
* Wallet files, private transaction notes, contacts, output labels and invoice records are local. Photo QR scanning uses the system picker and examines only the selected image on-device. Wallet directories use complete iOS file protection and are excluded from device backups. Wallet names and backup status live in a device-protected local manifest. Invoice data is encrypted with a key derived from the individual wallet password.
* The app obscures the switcher preview, locks when backgrounded or when iOS withdraws protected data, invalidates in-flight authorization, and disallows third-party keyboards. Copying a recovery phrase requires fresh authentication and confirmation. That clipboard item is device-local and expires after 30 seconds. A written recovery backup is essential if the device, its passcode or its Keychain credential is lost. Device compromise and photographs of recovery words remain outside these protections.
* New imports retain the original recovery words or keys in a separate authenticated encrypted file, scoped to the wallet and file purpose. Keep a seed passphrase separately. Earlier installations migrate a wallet’s credential when its owner next unlocks it. [Older backup formats](Recovery/README.md)
* The privacy checks report configured controls. They cannot establish anonymity. A view-only pairing QR grants access to incoming transaction information. An offline signer should stay offline on a separate device throughout its life.

## Network behavior

New wallets prompt for their own route before contacting a node. An offline signer never inherits the previous wallet’s online setting. Existing 0.1 wallets migrate their prior route on unlock. Automatic direct mode races health probes across eight named HTTPS endpoints and attempts the fastest healthy response first. It changes nodes after a failed connection or stalled scan. Selecting a named public node pins the connection to that endpoint. Custom mode lets the owner enter their own daemon. A direct connection exposes the device IP and the timing of scans or broadcasts to the node. Connecting to a remote node does not send a seed or a spend key.

Public HTTPS connections pass through an authenticated loopback relay and Apple's normal hostname and certificate checks. The native adapter refuses direct remote HTTPS because the pinned wallet2 client can accept unverified certificates under TLS autodetection. The relay forwards requests to the selected HTTPS origin, blocks redirects, and discards request credentials before forwarding. The native wallet treats the daemon as untrusted, including the relay.

Enabling Tor starts the bundled client. Users can also choose an existing local proxy. With Tor enabled, the app skips all HTTPS probes and connects exclusively to v3 onion nodes through wallet2’s explicit native SOCKS4a transport. It has no direct-network fallback. The built-in Tor directory contains ten onion addresses. Automatic mode probes their health through the selected loopback Tor proxy and starts with the fastest healthy response. A user can also select a named onion node and test latency through the active Tor proxy. Each manual Tor test sends only an HTTP get_info request over a SOCKS4a connection to the selected numeric loopback listener. Onion addresses come from the [Feather node directory](https://github.com/feather-wallet/feather-nodes/blob/5a1bd38a0a34c4de02ea034a2c4ed224005d2bbe/nodes.yaml). Importing signed key images requires a custom node and explicit approval to query spent status.

Enabling USD prices allows CoinGecko to see the IP address, the XMR/USD pair and the request time. Only public price queries leave the phone. The wallet computes every fiat equivalent locally. Consent lasts for the current unlocked session. It is unavailable offline or with proxy routing selected. The optional Live Activity displays only blockchain heights and scan state. When iOS grants background execution, the app locks its interface, drops decrypted UI state, and asks wallet2 to continue in scan-only mode. A watch-only wallet already lacks a spend key. When execution time or protected data becomes unavailable the app pauses scanning. Unlocking resumes normal sync. The source links open GitHub in the user's browser.

## Erasure

Settings provides individual wallet removal and full erasure. Full erasure requires typing `DELETE` and fresh authentication. The lock screen also provides device-passcode-authorized erasure. A confirmed full erase leaves a local journal until the app has cleared wallet directories, credential and biometric items, Tor state and preferences. The app can finish an interrupted erase after relaunch. Printed backups and copies previously shared with another device stay in their owners’ possession.

## Dependency review

Review the engine version, its differences from current Monero releases and the binary verification process in [the engine notes](ThirdParty/WalletEngine.md). Review legacy recovery code, test fixtures and package pins in [Recovery](Recovery/README.md). A matching download digest establishes which artifact is used. An independent rebuild and source-to-binary comparison are separate verification steps.
